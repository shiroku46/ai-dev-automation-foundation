# Agent operating contract

1. Before the harmless Bootstrap acceptance exercise in a newly bootstrapped repository, read `docs/PROJECT_STARTUP.md` and complete setup steps 1–5 for the exact repository. Successful acceptance is the final Phase 0 gate; product Issues and implementation start only after it passes.
2. Verify every setup item available through connected tools first. When repository-settings APIs are unavailable, instruct the owner once to open `Settings` → `Actions` → `General` → `Workflow permissions`, select **Read and write permissions**, enable **Allow GitHub Actions to create and approve pull requests**, and save.
3. GitHub repository access, enabled Actions/Foundation workflows, and both Workflow-permissions settings are mandatory before acceptance. A Codex environment or Claude credential is required only when that optional provider route is deliberately enabled; provider absence or quota must not block GitHub-only acceptance or product development. Do not request setup again after acceptance unless connected evidence shows it is no longer usable.
4. Read `docs/MINIMUM_SAFETY_PROFILE.md`, `SECURITY.md`, `docs/PROJECT_STARTUP.md`, and `docs/OPERATING_RULES.md` before acting.
5. Work from one trusted owner-authored Issue with a risk tier, bounded paths, acceptance criteria, prohibited effects, required checks, and rollback.
6. Before implementation, inspect every open same-repository Pull Request and reject overlapping live changed or renamed paths unless the Issue declares the exact dependency.
7. Use the connected GitHub App/API as the ordinary implementation route: create one dedicated same-repository branch, make GitHub-visible commits, and open or update one Pull Request.
8. Never push automation changes directly to `main` and never force-update a shared branch.
9. Treat local or provider-reported commits as advisory until the expected GitHub-visible remote branch head matches the reported SHA.
10. Require every changed and renamed path to match the Issue scope. Accept only exact repository-relative paths and bounded suffix patterns such as `tests/**`.
11. Require explicit protected authorization for workflows, permissions, authentication or Secret interfaces, supervisor/security policy, repository settings, billing, deployment/production, and destructive operations.
12. Keep contributor checks read-only with no Secrets, OIDC, or write permission. Never execute proposed-branch code in a job carrying Secrets, OIDC, or repository write permission.
13. Bind implementation completion, validation, coordinator review, recovery, readiness, and merge to the exact current GitHub-visible head SHA.
14. Require complete successful Foundation and configured product checks for the exact Pull Request head. Treat stale, incomplete, missing, pending, failed, wrong-workflow, wrong-repository, cross-Pull-Request, and candidate-modified-workflow evidence as absent.
15. Apply the risk-tier review rule: low risk requires one exact-head coordinator diff review; standard risk requires a nonempty structured exact-SHA coordinator review; protected risk requires explicit authorization plus separate coordinator scope/security and final correctness/race review passes on the unchanged exact head.
16. Codex and Claude are optional implementation helpers or second-opinion reviewers only. Neither provider is a completion, review, or merge dependency. Provider quota, setup, connection, or generic output is non-blocking and records `human_action_required: false`.
17. Any head change invalidates previous check and coordinator-review evidence. Repeat the risk-tier-required review on the new GitHub-visible SHA.
18. Do not ask a person merely to implement, press Merge, Approve, Retry, Close, resolve routine review state, or change routine workflow state.
19. Before any stop or merge, query repository metadata, the live Pull Request, every changed and renamed path, source Issue scope and protected authorization, fixed workflow identities, native and product checks, coordinator-review evidence and threads, permissions, idempotency, collisions, and alternative connected paths.
20. Persist routine stops only as deterministic sanitized records on the fixed non-default branch `automation-internal-stops`, with `notification: false` and `human_action_required: false`; provider unavailability is a routine non-blocking state.
21. Human notification is allowed only for the canonical account/provider UI reason codes after connected evidence proves no callable route exists. Quota exhaustion alone is never a human-only reason. Pre-PR Phase 0 Workflow-permissions guidance is delivered directly in the initiating project conversation, contains only non-secret navigation and the resume condition, does not call `human_only_notice()`, does not publish to GitHub, and does not create a new runtime reason code.
22. `ai-no-merge` always stops merge execution. Immediately before merge, re-fetch the live PR, exact head, source Issue, scope, checks, coordinator-review record, unresolved threads, hold state, default branch, and mergeability, then use expected-head-SHA protection.
